## Where requests run

- **The place button** — every request editor carries a button after
  **Save**: a run glyph beside the place's own mark — this machine's
  operating-system mark, or the server's icon, the same one the
  workspace switcher shows for it. Hover it for the words (*Runs
  locally: in the desktop app*, *Runs remotely: on <server>*) and click it for the reason, the
  alternatives and, where a place cannot run the request, the way to
  get it running. Nothing is forwarded silently and nothing is
  downgraded silently: a request that cannot run where it is set to
  says so and names the place that can.
- **Three places, as roles** — *This device* (the app's own network
  stack), *The desktop app* (this app, when a paired browser sends) and
  *The workspace's server* (the server that provides the workspace; an
  Org workspace has one by construction). A request's place is kept on
  this device, never synced, and resolves through this device's own
  connections. *Automatic* is the default everywhere: the request runs
  here when it can, otherwise on the one place that can.
- **Choosing a place** — the popover lists every place this device
  knows — *Desktop app* and *Server*, each with its mark; a row that
  cannot run the request stays visible but disabled, with the reason
  and the way to fix it (*Open Backup and Sync* for a server whose
  wire is down, *Available in a server workspace* for a personal
  one). A pick is a draft edit: the request runs there at once and
  **Save** keeps it — with the request, on this device only; a place
  names this machine's topology, so it never syncs to anyone else.
  The **Runs on** row on the request's Settings tab is the same value,
  *Reset to automatic* clears it, and a request with no place of its
  own follows **Settings › API Requests › HTTP › Execution place**.
- **What a delegated send carries** — the surface you send from is the
  request's context. It resolves everything it holds — variables, the
  environment, vault secrets, TOTP codes, client certificates, files,
  cookies, the pre-request script — and only then hands the resolved
  request to the chosen place, which opens the connection and streams
  the raw response or frames back. The post-response script, cookie
  capture, publish-on-run and the saved response happen here. A send
  to a server states in the place popover that the resolved values,
  secrets included, travel to it. A knob the place cannot apply is
  named on the same popover — today the context's cookie jar — never
  dropped in silence. Redirects are followed here, one hop at a time at the
  place, with the jar speaking on every hop.
- **Sessions too** — WebSocket, MQTT and gRPC sessions run on the
  workspace's server when the place says so, and a GraphQL
  introspection rides its query's place. A place that refuses a
  session shows the refusal on the timeline itself, naming the switch
  to turn on and where.
- **Sent from** — every response and every session timeline says
  which place answered, on the meta strip, with the details in its
  popover.
- **This app as a place** — a paired browser's request that runs on
  the desktop app is resolved in the browser and only its connection
  opens here, under the two switches in **Backup and Sync › Your
  devices**.

## Sign in to a server

- **Your own account, in the browser** — **Backup and Sync › Sign in
  to a server…** takes the server's address as one field (a host,
  host:port or the URL the administrator gave you; the scheme and port
  boxes are gone). The sign-in step's **Sign in on <host>** opens the
  server's own page in your system browser; you sign in there with
  your credentials or your identity provider and approve this device.
  The browser hands you back to the app, which comes to the front and
  reads **Signed in as <you> · <server>**; **Connect** finishes the
  join. Nothing is typed into the app and the password never leaves
  the browser; **Cancel sign-in** drops a sign-in in flight. The
  administrator's pairing code or token stays behind *Have a pairing
  code or token from an administrator?*.
- **One action per view** — the address step, the sign-in step and the
  Connect step each hold one primary action: **Next** only once signed
  in, **Check again** only when the server did not answer, no Back,
  and the Connect step names the place it joins. A declined sign-in
  comes back to the app as a verdict of its own, as an expired or
  abandoned one does, with **Try again** beside it.
- **Every server state reads honestly** — an unclaimed server says
  where its administrator is set up first; a server nobody can sign in
  to from a browser says the administrator's code or token is the only
  way in.
- **A joined server that granted nothing** keeps its group in the
  workspace switcher — *No workspaces — access not granted* with
  **Open <server>** to the server's own page — and the banner offers
  the same, dismissable per server until access is granted. The
  *Where they go* row hides while there is only one place.

## Settings

- **Proxy is a root of its own** — it sits after Backup and Sync in
  the settings tree; the Connectivity wrapper that held it alone is
  gone. Page ids and deep links are unchanged.
- **Trusted roots on macOS** — the Firefox row keys off the app bundle
  under Applications, one row per installed Firefox, instead of the
  profile folder macOS guards behind a data-access prompt; Firefox no
  longer vanishes from the trust stores, and the per-profile opt-out
  is retired with it. The helper's registration reads *Not found —
  macOS has no record of it; register again* in gold rather than
  blaming the install location, and a registration macOS answers with
  its own approval prompt reads as waiting for approval, not as a
  failure.
- **Server Admin › Server** shows the build's version and, for a
  build that ships no notes, says so instead of a blank tab.
