## Where requests run

- **The place chip** — every request editor carries a chip beside its
  **Send**, **Connect** or **Invoke** button: *Runs here*, *Runs on the
  desktop app*, *Runs on <server>* or *Needs the desktop app*. Click it
  for the reason, the alternatives and, where this surface cannot run
  the request, the way to get it running. An alternative is offered
  only while that place is connected — the desktop app's row when the
  extension is paired with a running app, the server's row when the
  workspace's server is reachable.
- **What runs where** — HTTP, GraphQL, WebSocket and MQTT over `ws://`
  or `wss://` run here, over the browser's own socket for sessions,
  with the desktop app and the server as alternatives. MQTT over
  `mqtt://` or `mqtts://` needs a raw TCP socket the browser cannot
  open: it runs on the desktop app or on the workspace's server, and
  *Automatic* picks whichever is connected. gRPC is forwarded to the
  connected desktop app, else to the workspace's server; with both
  connected the desktop app runs it and the server is offered beside.
- **Node-only knobs move the session** — a session over the browser
  socket cannot apply custom handshake headers, disabled SSL
  verification or the credential's handshake header. The chip names
  the ones the request has set, and the Settings tab unlocks them for
  a send that runs on the desktop app or the server.
- **Choosing a place** — four layers, the most specific one winning:
  the chip's **Run on** rows for this send only; the **Runs on** row on
  the request's Settings tab; the same row on a folder's or a
  collection's settings, inherited by everything inside; and
  **Settings › API Requests › HTTP › Execution place** for every kind.
  The values are roles, so they sync with the workspace and resolve on
  each device through its own connections. A role this surface cannot
  honour reads *Cannot run on <place> yet* and the popover offers the
  eligible places.
- **Resolved here, sent from there** — the extension is the request's
  context whatever the place: variables, the environment, vault
  secrets, TOTP codes, files, cookies and the pre-request script
  resolve here, and only the connection opens at the place, which
  streams the raw response or frames back. The post-response script,
  cookie capture, publish-on-run and the saved response happen here.
  A send to the desktop app carries nothing the vault does not already
  sync there; a send to a server states on the chip that the resolved
  values, secrets included, travel to it. The cookie jar is named as
  not applied at the place; redirects are followed here, one hop at a
  time.
- **Sent from** — every response and every session timeline says
  which place answered, on the meta strip, with the details in its
  popover. A place that refuses shows the refusal on the response or
  the timeline, naming the switch to turn on and where. The status row
  reads *runs requests* beside the desktop app while the global
  preference points at it.
- **When the chip asks for the desktop app** — a request no connected
  place can open reads *Needs the desktop app*, and its action follows
  what is installed: **Open in the desktop app** when it runs and is
  paired, **Open app** when installed and paired, **Connect** when
  never paired, **Download** when absent. Composing and saving work
  regardless.

## Sign in to a server

- **Your own account, in the browser** — **Settings › Backup and Sync
  › Sign in to a server…** takes the server's address as one field (a
  host, host:port or the URL the administrator gave you; the scheme
  and port boxes are gone). The sign-in step's **Sign in on <host>**
  opens the server's own page in a window of its own; you sign in
  there with your credentials or your identity provider and approve
  this device, the window closes by itself and the extension reads
  **Signed in as <you> · <server>**; **Connect** finishes the join.
  Nothing is pasted into the extension and the password never leaves
  the browser. On a browser without such a window the step shows a
  short code and a link with a copy affordance and *Open the page
  again*, and waits while you approve on any device — the page names
  this one, *Chrome · macOS*. The administrator's pairing code or
  token stays behind *Have a pairing code or token from an
  administrator?*.
- **One action per view** — **Next** only once signed in, **Check
  again** only when the server did not answer, no Back, and the
  Connect step names the place it joins. A declined sign-in closes the
  window and comes back as a verdict of its own, as an expired or
  abandoned one does, with **Try again** beside it; **Cancel sign-in**
  drops a sign-in in flight.
- **Every server state reads honestly** — an unclaimed server says
  where its administrator is set up first; a server nobody can sign in
  to from a browser says the administrator's code or token is the only
  way in.
- **A joined server that granted nothing** keeps its group in the
  workspace switcher — *No workspaces — access not granted* with
  **Open <server>** to the server's own page — and the banner offers
  the same, dismissable per server until access is granted. The
  *Where they go* row hides while there is only one place.

## Settings

- **Proxy is a root of its own** — it sits after Backup and Sync in
  the settings tree; the Connectivity wrapper that held it alone is
  gone. Page ids and deep links are unchanged.

## Languages

- **The store listing and the browser's chrome** — the extension's
  name, its description and the toolbar button's label follow the
  browser's own language across all eight: Français, Español, Deutsch,
  简体中文, 日本語, 한국어, Русский and Română.
