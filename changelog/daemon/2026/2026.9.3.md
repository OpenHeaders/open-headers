## Signing in from a client

- **The server is the authorization server for its own clients** —
  the desktop app, the extension and the CLI are three registered
  public clients (`openheaders-desktop`, `openheaders-extension`,
  `openheaders-cli`) of the server they join. The desktop app and the
  extension run the authorization code grant with PKCE — the desktop
  app returns on its loopback callback, the extension in the window
  its browser's identity API opened; the CLI, and the extension on a
  browser without an identity API, run the device authorization grant
  with a short code and a link. The server publishes its metadata at
  `/.well-known/oauth-authorization-server`; there is no registration
  for other clients and no refresh token — a session that expires is
  signed in again.
- **One consent page, two renderings** — where the web app is served
  and reached at a secure address (https or loopback) the page is a
  card inside the web app, approved in one click by a browser already
  signed in, after the usual sign-in by one that is not; elsewhere — a
  plain-http LAN address, a server serving no web bundle — the server
  renders the same page itself with the email and password form on
  it. An identity provider's round-trip works on both. **Allow**
  sends the browser to the client's registered return address with a
  one-shot code only that client can redeem; **Not me** sends it there
  carrying the refusal, so the window the client opened closes on a no
  as on a yes; a device grant settles on the page and the client's
  poll hears it.
- **Each device is a session** — an approved device appears under
  **Paired devices** as a session bound to that person, expires after
  `sessionTtlDays`, can be revoked on its own, and the revocation
  endpoint (RFC 7009) lets a client give its own session back.
  Deactivating the person revokes all of theirs. The admin's **Pair a device** and **Generate
  token** and `ohd show-token` are unchanged — tokens are for machines
  and for devices an administrator sets up by hand.
- **Admission** — the routes a client itself calls (the metadata, the
  device grant's start, the token and revocation endpoints, confirming
  a pairing code, the `/auth/*/meta` reads) accept the extension's own
  origin; the consent pages accept top-level navigations and
  same-origin form posts; codes the token endpoint does not know feed
  the per-peer failure budget like pairing-code guesses.

## Sessions, users and audit

- **`sessionTtlDays`** — a top-level `daemon.json` key (env
  `OH_DAEMON_SESSION_TTL_DAYS`, whole days, default 30) governs every
  session the server mints: the password login, the claim, an SSO
  completion and a device sign-in alike. The old `oidc.sessionTtlDays`
  placement is refused by naming the move.
- **Users need an email** — a user is admitted with an email or not
  at all, since every sign-in joins on it; **Set email** on a user's
  row repairs the ones admitted without, an invite can carry an
  initial password where the password is the login, and the password
  action waits on the email.
- **Audit** — `daemon.device-login` records one allow row per device a
  person approves, with the person as actor.

## Running requests for the clients it serves

- **Delegated sends** — beside the sends the server resolves itself
  (the CLI, MCP, chains), it now opens the connection for a request
  the sending surface already resolved — the served tab, the desktop
  app or the extension hands over the final request and its knobs, the
  server opens the socket, streams the raw response or frames back and
  stamps where it ran. HTTP, GraphQL, WebSocket, MQTT and gRPC all
  ride it; the server never reads the workspace for such a frame.
- **Gated like every peer send** — the two-tier opt-in (same-device
  browsers on by default, other devices off by default), the frame's
  workspace named and provided by this server, `workspace.write` as
  the peer's user on it, audited; a malformed frame answers a
  structured refusal, and a refusal names its tier.
- **The served tab's scripts run in the tab** — the web app carries
  its own Safe script sandbox, so the server no longer runs a served
  tab's pre-request or post-response scripts.
