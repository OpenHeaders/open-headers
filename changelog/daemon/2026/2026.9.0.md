## Setting up and signing in

- **Claim in the browser** — a fresh server has no admin until the
  first browser creates one: a browser on the server itself claims
  it freely; a remote browser presents the setup code the server
  prints as it starts (a new code every restart). `ohd show-token`
  stays the machine bootstrap for the desktop app and the extension.
- **Sign-in by email and password or single sign-on** — the login
  gate no longer offers a token field and no longer bypasses itself
  for local visitors; a server with neither SSO nor a password says
  so and points at the admin.
- **Admin declaration and SSO default grant** — `oidc.adminEmails`
  in `daemon.json` names the identity-provider accounts that
  administer the server, and `oidc.defaultGrant` gives every
  identity-provider login a workspace role on arrival; the declared
  admins retire any unbound tokens.
- **`serverName`** — names the deployment in the served tab's org
  chip and on the awaiting-access screen, instead of the container id.

## Roles and access

- **Server admin is a per-user role** — set from the console or, when
  no admin can reach it, with the new `ohd user set-admin
  <id-or-email>` (`--clear` revokes). Administering the server never
  grants workspace access; that stays with the per-workspace grants.
- **Invites carry access** — creating a user from the console grants
  the workspace access you pick after the seat gate, so the user
  arrives with something to open. `ohd user add` becomes the offline
  recovery hatch: it admits without access and tells you to grant.
- **Guests and visibility** — a **guest** role, per-workspace
  visibility (private, internal, public); members read an internal
  workspace read-only, owners flip visibility with an audit entry,
  and the served tab receives the offer or retraction live.
- **Owner self-service** — owners grant and revoke peers from the
  workspace's members modal; granted users can leave; the console
  reads last-seen per user.
- **Revocation evicts live** — a revoked user's open tabs and
  paired clients lose the workspace at once; a re-granted workspace
  re-sends its catch-up.
- **Service accounts** — a directory kind with no login and data-plane
  access only, created from the console.
- **Zero-workspace posture** — a server with no workspace yet shows
  its admin an explained empty state instead of a dead end.

## Public workspaces

- **Publish a read-only snapshot** — with `publicWorkspaces: true` in
  `daemon.json` (or `OH_PUBLIC_WORKSPACES=1`), the owner of a
  public-visibility workspace can publish a snapshot the server serves
  anonymously at `/public/<workspaceId>`; a review moment shows what
  the snapshot contains before it goes out. Turning the switch off
  darkens every publication without deleting anything.

## Status and operation

- **`ohd status` reports what is running** — the bind the server
  actually holds (loopback-only or every interface), the LAN join
  URLs, the pid, and whether `daemon.json` has moved on since it
  started (which needs `ohd restart`). A failed last run names the
  bind it could not take.
- **A bind conflict is a clean failure** — a port already in use used
  to crash the process through an unhandled socket error; the server
  now exits with the cause on its log line and `ohd status` explains
  the last run.
- **`--use-system-ca`** — also trust the operating system's
  certificate store on this machine, additively beside the bundled
  roots (needs Node 22.15 or newer); `useSystemCa` in `daemon.json` or
  `OH_DAEMON_USE_SYSTEM_CA` seed the same posture, and the start line
  and `ohd status` say when it is on.
- **Workspace trusted certificates apply on the server** — the
  workspace's CA roots and this device's pinned certificates apply to
  every HTTP, WebSocket, gRPC and MQTT dial the server makes and to
  the proxy's upstream leg.
- **Every dial identifies itself** — requests the server sends carry
  an OpenHeaders user agent with the version unless the request names
  its own.

## OAuth 2.0 on the server

- **Tokens acquired without a browser** — the `requests_authorize`
  and `requests_authorize_status` tools acquire a saved request's
  OAuth 2.0 token on the server: client credentials, password and
  JWT Bearer exchange at once; the device code grant starts and polls
  while the user approves on any device; the authorization code
  grant is refused with the fix. `oh request authorize <name>` drives
  it from the terminal.
- **A loopback callback route** — `GET /oauth/callback` on the bound
  port receives the authorization code flow's redirect for the
  desktop app; a headless server refuses that grant by name.
- **Signed assertions, DPoP and discovery** — `private_key_jwt`,
  `client_secret_jwt` and the JWT Bearer grant, DPoP-bound tokens
  with a proof on every hop, and OpenID discovery all run through the
  server's transport, so its proxy and trust settings apply.

## MQTT and session scripts

- **MQTT sessions** — the server dials `mqtt://`, `mqtts://`,
  `ws://` and `wss://` brokers for the clients it serves, with
  auto-reconnect, QoS 1 and 2 retransmission and the workspace's TLS
  settings.
- **Session hooks run on the server** — the WebSocket, MQTT and gRPC
  script hooks run in the server's script sandbox for forwarded
  sessions, the same as HTTP scripts.
